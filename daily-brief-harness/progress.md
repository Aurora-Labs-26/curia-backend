# M3 Progress — Generation Pipeline + Judging Pipeline

**What this is**: Curia's Daily Brief is a personalized news-podcast generator (fetch → rank/curate → write segment scripts → stitch into one brief). This repo is both the live pipeline ("System B": a two-phase Pre-Opt + Per-User Brief Cache) and its own eval harness/dashboard — a tool for freezing real runs as "gold" data, hand-labeling them, and validating LLM-as-judge verdicts against those human labels before trusting the judges for anything. `harness.eval_*` tables and the Gold Set tab are the harness; nothing in this doc touches the live user-facing send pipeline unless explicitly noted.

Working log of the M3 judging-analysis pass: what was found, what shipped, why, and what's still open. Originally scoped to 6 frozen gold profiles (Pure Tech, Biz-Finance, Casual Reader, Niche Topic, Near-duplicate, No-custom-topics); the gold-set workflow itself changed mid-pass (see below), so this now covers the whole arc, not just the original 10-item list.

**Status**: pushed and deployed in five rounds — `4f31e47` (relevance-judge max_tokens fix, score_curate concrete-claim gate, Judges-tab ordering/pooled-kappa cleanup), `0cf407f` (Judges/Hit-Miss tab UI redesign), `d7a3847` (column-width and show-more polish), `e2a30ba` (order-ranking flag, Judging #9), and `ef5cc96` (Score & Curate's model/prompt/pool-cap/Local-gate/Local-fetch work, #10-13). `db/008`–`012` have all been applied to both local dev and Railway (verified — see Migration log). Everything in this doc is now live on Railway.

## Gold Set workflow redesign

The original design froze exactly 6 named profiles, enforced by a hard DB trigger blocking any mutation of a frozen run's underlying data. Reframed mid-session: still in development (~a month from shipping), and the fixed-6/hard-freeze model was blocking the actual desired workflow — iterate on a pipeline prompt, regenerate, relabel, rejudge, repeat, for any user, not just the original 6.

- **`db/008_soften_freeze.sql`** — dropped the hard trigger that blocked `UPDATE`/`DELETE` on `eval_fetched_articles` / `eval_ranking_output` / `eval_llm_ranking_output` / `eval_segment_transcripts` / `eval_meta_segments` once a run was gold-active. Only `eval_fetched_articles` was ever actually load-bearing for gold labels; the rest have no gold data keyed against their content, so the trigger was blocking iteration for no validation benefit. `eval_gold_runs.is_active` stays as a purely informational pinned marker.
- **Freeze-a-Run UI** — a "pin any run" API already existed (`GET /api/eval/runs/recent`, `POST /api/eval/gold/runs/{run_id}/freeze`) but had no UI in front of it. Added a modal (pin icon next to Frozen Profiles) that browses recent `generate_brief` runs for any user and lets you pin one with a label of your choice, or unfreeze/relabel an existing one.
- **Delete-gold-run** — unfreezing never deleted the row (by design, reversible), so the list accumulates stale `(unfrozen)` entries over time. Added a delete button (shown only on already-unfrozen entries) that removes just the `eval_gold_runs` pin — doesn't touch the underlying `eval_runs`/articles/segments/labels, which become harmless invisible orphans.
- **Known workflow gotcha**: regenerating a brief for an existing gold-profile user (e.g. "generate brief" for Eval Bizfi) always creates a brand-new `eval_runs` row — there's no "regenerate into an existing run_id" path. The Gold Set tab keeps showing the old frozen run until you freeze the new one yourself (and separately unfreeze/delete the old one if you don't want both listed).

## Generation pipeline

### 1. Event dedup — DONE
`score_curate.py`'s Step 2 told the model to collapse same-event articles to one representative, marked "MANDATORY" — but wasn't being followed. Confirmed via direct DB inspection: Biz-Finance's `ranked_order` had the same SK Hynix IPO story 7 separate times (different outlets); Near-duplicate's had the same Iran-ceasefire storyline 6 times and the same "Trump fires election-commission members" story ~4 times. The deterministic embedding-clustering in `scoring_service.py` (0.72 threshold) already catches near-identical duplicates before this point — these survivors were same-event-different-wording cases specifically below that threshold, exactly what the prose instruction was supposed to catch instead.

**Fix**: within the same `score_curate` call, the model must now output an explicit `event_clusters` field (which article ids belong to each event, which is the representative) *before* `ranked_order` — forcing the dedup decision into structured, checkable output instead of a silently-applied prose rule. `ranked_order` is restricted to representative ids only. Deliberately shipped **without** a deterministic embedding backstop alongside it — one variable at a time, so if duplicate-count improves, we know why.

**Verified live**: triggered a real Pre-Opt run (Business topic). SK Hynix's IPO — 7 duplicates before — appeared exactly once in the fresh run's `ranked_order` (21 total entries, down from 52-112 in old un-deduped runs).

### 2. Missing/headline-only source text not surfaced to the generator — DONE
`content_fetched: False` (real article-text fetch failed, only a headline/description available) was tracked internally but never reached the `article_segment` prompt — the model didn't know it only had a headline, so it invented specific facts/quotes/numbers freely. Traced to 11 of 12 (92%) "critical" faithfulness-judge flags.

**Fix**: threaded `content_fetched` through `ArticleSegmentRequest` → both `user_brief_runner.py` and `preopt_runner.py` → the segment prompt, with an explicit "stay vague, don't invent specifics" instruction when it's `False`.

### 3. Ranking blended relevance and significance into one judgment — DONE
Risked either noise (too much relevance weight) or an off-topic-but-huge story surfacing (too much significance weight) — the latter is worse, since suggesting something irrelevant is embarrassing regardless of how big the story is.

**Fix**: restructured both Step 3 (non-local) and Step 4 (local) into two explicit sequential phases within the same call — Phase A is a hard topical-relevance gate (in/out, not a weight), Phase B ranks only Phase A survivors by real-world significance. The local gate's "must connect to a requested topic OR be a major local event any resident would want to know" mirrors the already-fixed relevance judge rubric, so generator and judge stay aligned on what counts as a valid local pick. This lines up with the order-correctness judge's own disagreements (its preferred alternatives were always on-topic, just more significant).

Calibrating how strict the gate is (too loose → noise persists; too strict → cuts borderline-good stories) needs real iteration across profiles — not resolved by this change alone, needs your ongoing judgment as you relabel.

### 3b. Phase A's gate missed genre violations (newsletters/roundups) — DONE, needs broader validation
Found analyzing Eval-Bizfi: rank #1 non-local was a Morningstar "Smart Investor" weekly newsletter (`full_text` literally opens "Sign up for my weekly newsletter... This week's highlights:", bundling 5 unrelated market items) — exactly what Phase A's own exclusion list already named ("newsletters," "daily roundups"), but the model cherry-picked one bullet (SK Hynix IPO) from inside it and ranked the whole digest as if it were a dedicated single-event story. Same failure shape as Generation #1's original dedup bug: a prose-only exclusion rule with no structured, checkable output — nothing in `ranked_order` can distinguish "correctly gated out" from "just didn't rank high" from "lost during dedup."

First fix attempt (adding the gate as a per-cluster `valid`/`exclude_reason` field, still keyword-listing "newsletter/roundup" as categories) caught a *lot* of previously-invisible junk (opinion "stock about to explode" spam, "Top X" lists, off-topic farmers'-market noise — 23-27 of 50 clusters flagged, none of which were being filtered before) but still missed the Morningstar piece itself, consistently, across 2 runs — its title reads as thematically coherent ("stock/bond markets," "globalization," "SK Hynix IPO" are all related financial themes), unlike a blatant two-unrelated-companies-glued-together title, and `score_curate` never sees `full_text` (deferred to the 4 winners only, for cost reasons), so the "this is actually a newsletter" tell was invisible to it.

Sharper fix (your framing, not a hedge): a genuine news headline names one specific subject doing/announcing/experiencing one specific thing (e.g. "SK Hynix Stock Surges in US IPO"). The Morningstar title names *themes* ("Second-Half Stock and Bond Market Opportunities," "Globalization Isn't Dead") without asserting anything concrete about any of them — that's a fully general, content-agnostic test, not a keyword match, and it doesn't require recognizing "Smart Investor" as a branded column. Rewrote Phase A's gate around this "concrete-claim test" as the first, primary criterion, reinforced again at Final Validation (the recency-weighted position right before output).

**Fix**: folded the gate decision into Step 2's existing per-cluster `event_clusters` output (`valid: true/false` + one-word `exclude_reason` on each representative) instead of a new separate `excluded_ids` enumeration — clusters are far fewer than raw articles, so this is a handful of tokens, not a second full-pool listing (which would risk the same max_tokens ceiling just fixed for the relevance judge, below). This let Phase A's block be deleted from Step 3 entirely and the "prefer positive at rank 1" guidance (previously stated 3 times across Phase B) collapse to once — net prompt got *shorter*, not longer.

**Verified live** against the same Eval-Bizfi 54-article pool: both post-fix runs correctly caught the Morningstar piece (`valid: false`, `exclude_reason: superficial`) *and* a second, previously-unflagged case of the same pattern — AP's "America In Focus: Fed officials divided on US inflation views; US home prices hit all-time high" (a named recurring digest format splicing two unrelated claims). Neither appeared in `ranked_order` in either run. Token usage stayed well under budget (~22.5k in / 3.6-4.3k out vs. a 12000 cap).

**Known caveat, not fixed, not new**: Phase A's separate topical-relevance/opinion sub-check (unchanged today, just newly made visible) shows real run-to-run variance — one run flagged "Iran moves to close Strait of Hormuz. Should investors fear a Nifty crash?" as `off_topic`, which looks wrong (squarely Markets/Stocks-relevant, gold-labeled "hit" earlier). This variance existed before today, invisibly; structuring the gate just made it observable for the first time. Not chased further yet — needs validation across more profiles/pools during your relabel pass before this gate is fully trusted, same as Generation #3's original gate-strictness calibration.

### 4. Generic, content-agnostic transition opener per segment — DONE
Every non-lead segment opened completely cold, no acknowledgment of moving to a new topic — confirmed against real transcripts, and consistent with brief_coherence scoring 2-3/5 across every one of the 6 profiles.

**Critical constraint surfaced mid-discussion**: segment transcripts (and their TTS audio) are cached and reused across *different users* in production — a cost optimization, since TTS is far more expensive than the LLM call. That rules out any transition referencing the *specific* previous topic: a cached segment will eventually play after a completely different preceding segment for some other user, and a specific reference would be an audible, unmissable bug. (Recorded as a standing memory note for future prompt work: [[daily_brief_segment_cache_constraint]].) This also killed an earlier, more complex idea of threading the previous segment's title into the next segment's prompt — not just unnecessary, actively wrong given the caching model.

**Fix**: pure prompt/style-guide change, zero schema or code threading. `article_segment_style_guide.py` had an explicit rule *against* any transition — flipped to permit a short, generic, content-agnostic acknowledgment of movement, tailored per segment type (standard gets generic openers like "So, here's another one—"; local gets "closer to home"-flavored openers), never naming what it's moving from. Lead segment untouched (follows the intro directly, doesn't need one).

**Verified live**: same Pre-Opt test run produced 3 standard segments with distinct, natural, non-templated openers ("So here's something brewing in the business world right now.", "So here's something worth paying attention to.", "So here's something that just happened on Wall Street.") — real variety, no reference to prior content. Genuinely hard part, flagged up front: a generic phrase is a *tighter* needle to thread than a specific one, and needs enough variety not to feel formulaic across a whole brief — expect more iteration here as you listen through real generations.

## Judging pipeline

### 1. Relevance judge rubric — DONE (twice)
First pass: dropped the "matches interest *or* home location" tautology (was auto-passing anything merely set in the listener's city — local-pool direct_hit rate was 89% judge vs. 33% gold) and added a redundancy rule (duplicate coverage of the same event shouldn't all be direct_hit). Pooled kappa 0.166 → 0.294.

Second pass (see "Binary relevance label" below): collapsed the 3-way label to hit/miss entirely, rubric now explicitly mirrors Generation #3's Phase A gate criteria. Niche Topic's kappa (the one profile judged with fully consistent fresh data) jumped to 0.696 — fair → substantial agreement.

### 2. Faithfulness judge conflated two failure modes — DONE
Fabrication against a real, available article vs. invented detail because no real source text was ever fetched (Generation #2's root cause) were both reported as identical "critical" severity, overstating how often the generator hallucinates against real reporting.

**Fix**: `judge_faithfulness_article` now tags `source_available` (mirrors `content_fetched`) in its stored detail; the Judges-tab spot-check table shows "— no source fetched" next to affected rows. **Verified live**: re-ran judges for Niche Topic — 2 of 4 faithfulness_article rows correctly tagged `source_available=False`, including one genuine `source_available=True` critical flag (real fabrication, distinct from the headline-gap cases) — the diagnostic distinction works as intended.

### 3. Order-correctness — DONE
Old validation derived "gold" from the pipeline's own historical rank (falling back to it whenever no human significance label existed) — close to circular, since it mostly measured whether the judge agreed with the pipeline's past self. Confirmed the judge's actual reasoning was sound regardless (its "disagree" verdicts consistently picked more genuinely significant alternatives) — the metric, not the judge, was the problem.

Confirmed direction: validate the single top pick per pool, not full top-4 ordering (cheaper, more decidable, matches what's editorially highest-stakes, lines up with Generation #3). Split into two explicit questions, one per pool — the judge already did this (separate calls/rows for non-local vs. local); what was missing was a real human answer for each.

**Fix**: two new nullable boolean columns on `eval_gold_runs` (`non_local_top_correct`, `local_top_correct`; `db/009_order_correctness_labels.sql`), a toggle in the Ranking sub-tab next to each pool's #1 entry (unmarked = agree, matching the existing significance_rank convention), and `compute_order_correctness_agreement` now reads these direct labels instead of the derived-rank proxy. **Verified live and in a real browser**: flag → warning badge → undo → clean reset, zero console errors; kappa computation runs correctly (currently 0.0 pooled since no labels have been set yet — expected until you start using the toggle).

### 4. Diversity check widening — suppressed
Dedup (Generation #1) should cover the underlying case. No action taken.

### 5. Relevance judge silently returns zero results on large pools — DONE
`max_tokens=6000` for the relevance judge step could be entirely consumed by extended thinking on large pools, leaving zero output tokens — confirmed exactly this analyzing Eval-Bizfi: the relevance table only ever showed local-pool rows, never non-local. Reproduced live against the real 54-article non-local pool: `output_tokens_details.thinking_tokens=5391` out of a 6000 cap, leaving ~600 tokens for output — truncated mid-JSON, parse failed, `judge_relevance` silently returned an empty list (not an error, just zero rows) for that pool.

**Fix**: bumped `max_tokens` to 16000 for step 8 only. **Verified live**: same 54-article pool now completes cleanly (`stop_reason: end_turn`, ~7.4k total output tokens, comfortable headroom below the cap) with all 54 articles labeled. Re-ran judges for real — relevance table now shows 54 non-local + 5 local rows (was 0 + 5).

### 6. Segments query missing `ORDER BY` — DONE
Traced an apparent "intro order doesn't match segment order" bug that turned out not to be a generation bug at all: `user_brief_runner.py` provably builds the intro's story list and the segments from the exact same ordered selection list. The real bug was in `eval_logging_service.get_run_for_judges`'s segments query, which had no `ORDER BY` — since segments are generated concurrently (`asyncio.gather`, intentional, for latency), the DB returned them in whatever order those concurrent calls happened to finish, not broadcast order. That scrambled order was feeding brief_coherence's "order mismatch" complaints — a judging-harness artifact, not a real generation defect.

**Fix**: added `ORDER BY` (join through `url` to `eval_llm_ranking_output.rank`, `is_local` ascending so non-local segments precede the local one). **Verified live**: re-ran judges for Niche Topic post-fix — brief_coherence's complaint shifted from describing a scrambled order to a genuine qualitative transition gap between two now-correctly-adjacent segments (exactly what Generation #4 targets).

### 7. Judges-tab spot-check table grouped by judge_name, not broadcast order — DONE
The spot-check table (faithfulness/tone-flow/coherence/overview-fidelity) looped over judge names first, then sorted within each name by segment — so it rendered every `faithfulness_article` row (lead/standard/local) before every `faithfulness_bookend` row (intro/outro), displaying lead→standard→local→intro→outro instead of real broadcast order.

**Fix**: flattened every spot-check judge's rows into one list and sorted by true segment position (intro→lead→standard(s)→local→outro) across all of them together; `brief_coherence` (judges the whole stitched brief, no segment of its own) pinned after outro instead of falling into a null/0 sort key that put it first arbitrarily. **Verified live** in a real browser against Eval-Bizfi: intro rows (`faithfulness_bookend`, `overview_fidelity`) → lead → standard ×3 → local → outro (`faithfulness_bookend`) → `brief_coherence` last, zero console errors.

### 8. Pooled kappa across every profile — removed
The Judges tab showed "Pooled across every profile judged so far: relevance κ=... order correctness κ=..." below each profile's own numbers — mixed profiles at completely different iteration stages into one number nobody could act on, and had no consumer besides that one display line.

**Fix**: removed the display line, and removed the underlying pooled computation from `compute_relevance_kappa`/`compute_order_correctness_agreement` in `eval_judges_service.py` — not computed at all now, not just hidden. Both functions return `{"per_profile": {...}}` only, which is what the UI actually reads.

### 9. Order-correctness only checked the #1 pick, never ranks 2-N — DONE (not yet deployed)
Order-correctness validation (#3 above) only ever asked one question: is the #1 pick genuinely the most significant story in the whole pool? Nothing validated whether ranks 2 through the labeling window (8 non-local / 4 local — the same window already used for relevance hit/miss) were placed in sensible relative order. That's a real gap: which story lands at rank 2 vs. 4 changes how much airtime it gets (segments get progressively shorter after the lead) and how it's billed in the Intro's preview, so a misordering there is a real, listener-facing issue, not cosmetic.

Considered checking every adjacent pair (rank 1-vs-2, 2-vs-3, etc.) and rejected it as more than needed — too many new buttons, too much labeling effort for what it'd add. Landed on one more holistic yes/no per pool instead, same idea as the existing "is #1 right" check, just asking about everything below it as a whole.

**Fix**: the order-correctness judge now answers two questions in the same call (no extra API cost) — the original "is #1 right" question, plus "are ranks 2 through N placed in defensible order?" A second red button sits right next to the existing "Flag if top pick is bad" in the Hit/Miss tab: **"Flag if #2-8 order is bad"** (non-local) / **"Flag if #2-4 order is bad"** (local) — same unmarked-means-agree convention as every other label here. New DB columns (`non_local_order_correct`/`local_order_correct`, `db/012_order_ranking_label.sql`), a new "Order ranking (#2-N)" row in the Judges tab's kappa summary, and a second row per pool in the Order correctness report table.

**Verified live** against Eval-Bizfi: the new check immediately caught a real issue distinct from the #1-pick problem — it flagged the Iran/Strait-of-Hormuz story as misordered at rank 3, below a generic IPO-trend piece at rank 2, while the local pool's #2-4 order was judged fine even though its #1 pick was flagged wrong. Confirms the two checks catch genuinely different problems, not the same thing twice.

### 10. Score & Curate ran on the weakest model in the stack — DONE
Every generation step ran on `ACTIVE_MODEL` (Haiku); only judging steps got the stronger `JUDGE_MODEL` (Sonnet), per the buildplan's self-preference-bias mitigation for judging specifically. Score & Curate was never reconsidered for the same upgrade, even though it's the hardest reasoning task in the pipeline — cluster up to 150 raw articles into real-world events, gate each cluster, then produce a full significance ranking, all in one pass.

Confirmed live on a real 80-article pool (Eval-Bizfi): 7 separate wire-service pickups of one breaking event (market reaction to Iran/Israel strikes) survived as 7 separate valid clusters instead of collapsing to one representative. A same-prompt, same-data replay against Sonnet instead of Haiku collapsed all 7 correctly — isolating this as a model-capability gap, not a prompt-wording gap.

**Fix**: `llm_service.py`'s step-routing set (renamed `JUDGE_STEP_IDS` → `STRONG_MODEL_STEP_IDS`, since it's no longer judge-only) now includes step 3. Cost implication is real and different from the judge upgrades: this runs on every live brief generation, not just offline gold-run testing.

**Known ceiling, not fully solved**: Sonnet's own non-optional extended thinking burns the large majority of its output budget regardless of prompt wording — confirmed via `response.usage.output_tokens_details.thinking_tokens`: 85-90% of the budget on every real test, even after adding an explicit "work efficiently" instruction, a more procedural clustering rewrite, and a compressed final-validation step to the prompt (all three kept — reasonable on their own merits — but none meaningfully moved this number). The Anthropic SDK also hard-rejects non-streaming calls above ~21,333 tokens (`_calculate_nonstreaming_timeout`); `call_llm` has no streaming support, so `max_tokens=20000` for step 3 is close to the actual ceiling available, not a tuned number.

**Not tried**: the API also exposes an explicit `thinking: {"type": "enabled", "budget_tokens": N}` param that would cap reasoning at a fixed number instead of leaving it adaptive/uncontrolled — `call_llm` never sets `thinking` at all today, for any step, so every strong-tier call is implicitly adaptive. Left alone deliberately: capping it risks reintroducing the shallow-reasoning failure this whole change was meant to fix, and picking a safe number needs real testing this pass didn't get to.

**What actually worked**: shrinking the input pool, not the prompt — see #11.

**Separately surfaced, unrelated to the above**: judge calls (`eval_judge_outputs`) don't log token usage at all — no `input_tokens`/`output_tokens` columns, unlike segment/meta generation logging, which does. There's currently no way to see real Sonnet spend from the data, only by instrumenting a one-off diagnostic call and reading `response.usage` directly, which is how every number in this section was actually obtained.

### 11. Custom-topic / local article caps retuned — DONE
`CUSTOM_TOPIC_POOL_SIZE` 20 → 10: directly the fix for #10's truncation (an 80-article pool wouldn't finish inside the token ceiling; a ~43-article pool completed cleanly, `end_turn`, with correct dedup). Separately quality-checked whether 10 vs. 20 changes *content* quality across 9 sample custom topics (AI, Startups, Generative Music, Cryptocurrency, Personal Finance, Apple, Humanoid Robots, Climate Change, K-pop) — mixed and topic-dependent (cap=10 is cleaner for some, e.g. Apple; cap=20 rescues real diversity a thin cap=10 sample missed for others, e.g. K-pop), but for topics representative of this product's actual expected audience (Tech/Business/AI/Startups-adjacent), cap=10 held up fine or better. The token-budget reason alone is sufficient justification regardless of the quality read.

`LOCAL_POOL_SIZE` stayed at 20 (tried 10, reverted) — quality-checked the same way across 5 cities (Mumbai, Bangalore, Delhi, Hyderabad, Bhopal): cap=20 clearly rescues real story diversity in 2 of 5 (Bangalore, Delhi), is a wash in 2 (Bhopal, Hyderabad — bad regardless of cap that day), and is worse in 1 (Mumbai, where cap=20 just added more copies of the same 3 stories). Net: 20 stayed.

Also surfaced, not yet acted on: severe single-story redundancy in local pools (Hyderabad: 9 of the first 10 raw articles belonged to just 3 clusters) and single-source concentration (Bhopal: ~80% of results from one outlet's local bureau). Local's Step 4 still has no event-dedup step at all — `score_curate.py`'s own comment says it was left out for lack of "an observed instance of this failure"; these five cities are five observed instances now.

### 12. Local's relevance gate allowed a significance bypass — DONE
Step 4 Phase A's gate was OR: connect to a topic, *or* be a major local event regardless of topic. That let a significant-but-off-topic local story (a crime, a fire, a public-safety incident) into the brief even for a listener with narrow, unrelated stated interests. Confirmed live: fetched real Bangalore local news for a Business/Tech/AI/Startups/Music profile and found the entire raw pool (a murder, an assault, a drunken-brawl death, several human-interest pieces) would have passed the old OR-gate via the "major event" branch despite zero topical connection.

**Fix**: Phase A is now a strict AND — topic relevance required, no significance-based exception, matching the explicit principle "zero local articles is better than one that's significant but off-topic." The relevance judge's rubric (`relevance_judge.py`) had the identical OR-branch (deliberately mirrored, per its own header comment) — updated in the same pass so generator and judge stay aligned, same pattern as every other rubric-alignment fix in this doc.

### 13. Local's own fetch query never looked for topic-relevant news in the first place — DONE
Traced why #12's AND-gate returns empty so often: Local's fetch (`user_brief_runner.py`) was a bare, topic-agnostic search — `"{location_name}"` alone, never combined with the user's beats/custom topics. That was the right match for the old OR-gate (generic significant local news was supposed to have a chance), but under the new strict AND it mostly just wastes fetch budget on articles the gate will reject regardless of significance — confirmed empirically across the same 5 cities: a bare-location fetch surfaced at most 1-2 topically-relevant articles per city out of 20.

**Fix**: Local's query now combines the mandatory location term with an OR-group of the user's own topics (beats + custom) — `"{location}" ("{topic1}" OR "{topic2}" ...)`, same OR-join syntax already used elsewhere in `news_service.py` for beats with no Google topic-code. Falls back to the bare location query only when a user has stated no topics at all, matching Phase A's own carve-out for that case.

**Verified live** across the same 5 cities with a representative Tech/Business/Jobs/Startups/AI profile: Delhi and Hyderabad went from near-zero topic-relevant local hits to a clear majority (9-10 of 14, and ~9-10 of 10, respectively) — real IIT/AI-summit/chip-HQ stories instead of civic/crime noise. Bhopal stayed thin (only 2 results) but both genuinely relevant. Bangalore and Mumbai are the honest caveats: Bangalore's combined query found almost nothing that day (a real supply gap, not a bug), and Mumbai returned its full 20-cap but mostly noise, with one outlet (Mid-day) and one outlet-name coincidence ("Business Today") dominating results that don't actually connect to the stated topics.

**Known real risk, deliberately not "fixed" here**: a keyword-based fetch can't distinguish genuine topical relevance from incidental mentions — confirmed live twice (an "AI engineer kills woman colleague" murder-suicide story matched purely on the victim's job title, under both the OR-query and a plain two-term AND-query variant that was tried and rejected). This is squarely what Phase A's LLM gate is for, not something the fetch layer can or should try to solve — explicitly not touching the AND-gate to work around this.

Also tried, and rejected: querying `location AND topic` separately per topic (5 queries instead of 1, capped at 4 each) instead of one OR-combined query. Worse overall for this topic set — wastes fixed budget on topics with zero local supply that day (Business/Jobs/Startups came back empty in most cities), while the one reliably productive topic (AI) got throttled to the same small cap as the empty ones. The single OR-query's adaptive budget allocation won 3 of 5 cities outright.

## Judges tab UI/UX redesign

The Judges/Ranking tabs worked, but were built for the primary user's own dense working style — teammates trying to use the same dashboard found it genuinely confusing (jargon-y headings, raw judge_name strings, article titles instead of segment positions, an unreadable [severity] wall of text). Reworked end-to-end for a third party to actually use, not just the person who built it:

- **"Ranking" tab → "Hit/Miss"**, and its top-pick flag button renamed to "Flag if top pick is bad" and restyled loud red — it's the single most consequential label in that tab (it's what order-correctness kappa validates against), so it shouldn't look like every other neutral toggle.
- **Kappa summary**: "Validation vs. M2 gold data" → "LLM v/s Human Agreement (Kappa Values)"; dropped the `n` column (redundant with what's already shown per-row in the tables below); "Run Judges" moved out to its own top-right corner action. This took two iterations — first attempt boxed the kappa table and the button together in one card, which the user correctly called out as bad hierarchy (Run Judges re-runs *every* judge — relevance, order-correctness, faithfulness, tone/flow, coherence — not just the two with kappa numbers, so nesting it inside a card titled specifically about kappa values misrepresented its scope). Settled on: no shared box, button top-aligned with the kappa heading, "some padding" from the panel edge.
- **Hit/Miss Choice Comparison** (was "Relevance (vs. gold label)"): "Gold label"/"Judge label" → "Human label"/"LLM label"; split into two separate tables (Non-Local, then Local) instead of one table with "Non-local #3" baked into every row — each table's own header now says "Article (Non-Local)"/"Article (Local)", rows just say "#3 — title". Unlabeled cells show "—" instead of the more verbose "(unlabeled)"; match/differ is a green check / red X icon instead of text. Unlabeled rows (the majority on a 50+ candidate non-local pool) are collapsed behind a small "Show N more" by default instead of drowning the labeled ones.

## Data/schema hygiene

- **`significance_rank` removed entirely** (`db/010_drop_significance_rank.sql`) — was only ever consumed by the old order-correctness derived-gold logic, fully replaced by Judging #3's direct labels. Removed the input field from the Ranking sub-tab, the column from the DB, and every reference in between. Verified via full-codebase grep before and after.
- **Relevance label collapsed to binary (hit/miss)** (`db/011_binary_relevance_label.sql`) — was a 3-way `direct_hit`/`tangential`/`miss` enum. Two reasons: (1) the generation pipeline's own relevance gate (Generation #3, Phase A) is itself binary IN/OUT, not a 3-way weighting, so the label should validate what the gate actually does; (2) nearly all kappa disagreement noise traced back to the `direct_hit`-vs-`tangential` boundary specifically, not to genuine misses. Migration safely widens the column to `text`, collapses `direct_hit`+`tangential`→`hit`, then re-narrows to a freshly-defined 2-value enum — written to be safe against real existing data (not just an empty DB), since this will eventually run against Railway's data too. **Verified**: 86 label rows before and after (zero data loss), exact expected collapse (56+9 hit = 41+15 direct_hit + 7+2 tangential), idempotent (re-ran bootstrap twice, identical counts), and a live judge re-run confirmed real verdicts are now purely `hit`/`miss` with Niche Topic's kappa at 0.696.

## 1. The headline finding: he found our bug, and our diagnosis was wrong

`pyproject.toml` on `v3` **never included `googlenewsdecoder`**. The port brought the
`from googlenewsdecoder import gnewsdecoder` import (inside a broad `try/except`) but not
the dependency — so in prod, every decode "failure" was actually an **ImportError**,
logged as `decode_or_fetch_error`. Our "Google blocks the ECS egress IP" theory
(29/29 failures last night) was wrong; the module was simply not installed.

Consequences of his one-line dependency fix once deployed:
- The decode fast-path comes alive for the first time in prod.
- `resolved_url` (migration 0036) finally starts populating → real publisher links.
- Our cascade-on-google-url fallback (`ffac614`) demotes to what it should have been:
  a genuine fallback for the rare real decode failure, not the primary path.
- Faithfulness flag rates should drop further (more real source text).

He also added `edge-tts` to pyproject — harmless, but its comment ("active episode TTS
binding") is stale: episodes are on cartesia-sonic since `0d8c0e6`.

## 2. What the branch delivers, by subsystem

### Scheduling + delivery (the missing production loop)
- **`worker/main.py`**: two new APScheduler jobs — Pre-Opt every 6h (correct reasoning:
  no single UTC hour is "before everyone's slot" across timezones), and a 15-min
  dispatch poll that enqueues `generate_brief` (background lane) for due users.
- **`store.list_due_users_for_generation`**: single SQL query, `now() AT TIME ZONE
  u.timezone` per user, `>=` comparison (outage-tolerant, not window-matched), anti-join
  that excludes `generating`/`ready` but **retries `failed`** — a deliberate fix over
  "any row exists" which would have silently never retried a failed brief. Good design;
  see §4.1 for the one flaw and §4.2 for the retry-loop cost cap.
- **`local_date` threading**: the job payload carries the user-local date computed by the
  query, not recomputed in the handler. Correct — avoids UTC/local date skew.
- **`core/notifications.send_brief_ready`**: event-triggered FCM push, fired after the
  audio attempt (so tapping the push doesn't land on a ready brief with no audio yet),
  deduped per (user, type, date) via the existing notification_log claim pattern with
  release-on-failure. Clean.

### Prefs UX (`/brief/preferences`)
- **`GET /preferences`** added — pre-fills the edit sheet. Straightforward.
- **`PUT /preferences` contract changed** (breaking, intentional):
  `location_name` now optional (IP-derived via new `brief/geo.py`; explicit value = the
  "wrong city?" correction and always wins); adds `scheduled_time` ("HH:MM") +
  `timezone` (IANA, from `Intl.DateTimeFormat`); returns `200 {"location_name": ...}`
  instead of a bare 204 so the UI can show "Local news: <city>". A failed IP lookup
  never wipes a previously resolved city. All sensible; the client must ship in tandem.
- **`create_user_with_topics` now prunes** de-selected topic links — fixes a real bug we
  shipped (`link_user_topic` is additive-only, so beats could never be deselected).
- **`brief/geo.py`**: ipapi.co lookup, once per prefs-save. The X-Forwarded-For handling
  counts from the RIGHT (`BRIEF_GEO_XFF_INDEX`, 2 in prod for CloudFront→ALB), which is
  the spoof-resistant direction — client-prepended junk can't shift the offset. Private/
  reserved IPs refused; everything fails soft to "no Local Pulse". Correct and
  well-documented. Deploy dependency: §5.2.

### Runner hardening
- **No-city path**: `user_brief_runner` now skips the local fetch entirely instead of
  interpolating an empty string into the Google News query (`'"" (Tech OR ...)'`) — a
  latent bug in the port that IP-derived (possibly empty) cities would have triggered
  daily. Brief ships with 4 segments, local slot already optional downstream.

### Playback (client parity with episodes)
- **Migration 0037**: `users.timezone` (NOT NULL default UTC) + `daily_briefs.
  play_progress/listened/last_played_at`, mirroring episode columns. Chains 0036 → 0037
  correctly; clean downgrade.
- **`PUT /brief/{id}/progress`**: ownership enforced in the WHERE clause (user_id match),
  404 on zero rows. Mirrors episodes.
- **`GET /brief/today/audio`**: S3 presign vs local range-streamed file, branching on

- **`GET /brief/today` redesigned**: distinguishes "prefs never set" (404) from "prefs

  run (intro/outro text + chapter offsets) in one call. This matches how our audio pass
  reads the manifest — consistent.

## 4. Issues to fix (ranked)

### 4.1 One bad timezone bricks scheduling for everyone — fix before merge
`list_due_users_for_generation` is a single query over all users; `now() AT TIME ZONE
u.timezone` makes Postgres validate the zone name **at query time**. One user row with a
garbage timezone (any client bug — the column is written straight from the request) makes
the whole query throw, and the dispatch loop then delivers **no briefs to anyone**, every
15 minutes, until the row is fixed. His docstring frames erroring as "the right failure
mode for a scheduling bug" — for one user, yes; as a global outage, no.
**Fix**: validate at the API edge (`zoneinfo.ZoneInfo(tz)` in `PUT /preferences`, 422 on
failure) — one guard clause + test. Optionally also defend the query with a
`WHERE u.timezone IN (SELECT name FROM pg_timezone_names)` semi-join.

### 4.2 Failed briefs retry every 15 minutes, forever — cap it
Retrying `failed` is the right default, but a *permanently* failing generation (bad data,
LLM refusing) re-enqueues ~96×/day at full pipeline cost (LLM + judge calls). Add either
an attempts column checked by the dispatch query, or exclude `failed` rows whose
`created_at` is today and count ≥ N. Post-merge is fine; worth doing within days.

### 4.3 Dual-scheduler double-dispatch (pre-existing pattern, now with cost attached)
`_start_scheduler()` runs in **both** worker services (interactive + background), so both
run the dispatch poll and Pre-Opt on their own clocks. The notification crons already had
this shape (deduped by notification_log). For dispatch, the enqueue→row-creation window
(~seconds) means two dispatchers can both enqueue the same user; two concurrent
`generate_brief` runs for one (user, date) then both execute the full pipeline —
`daily_brief_articles`' `(brief_id, segment_type, rank)` unique constraint makes the
loser *fail* rather than corrupt data, but the LLM spend is doubled and a spurious
failure is logged. Pre-Opt every 6h × 2 schedulers also doubles a Sonnet-heavy batch.
**Fix**: gate `_start_scheduler()` (or just these two jobs) behind an env flag set on
exactly one service (e.g. `CURIA_SCHEDULER=1` on worker-background only). Small change;
do it at merge time since Pre-Opt cost doubles otherwise.

### 4.4 Minor
- `edge-tts` dependency comment says it's the active episode binding — stale; cartesia is.
- `uv.lock` not regenerated (Docker uses `pip install -e .` so prod builds resolve fresh;
  local `uv sync` users need a lock update at merge).
- Bearer token in `?token=` query strings (audio routes) can land in access logs — this
  is the pre-existing episode pattern extended, not new exposure; fine for now, worth a
  short-lived signed-URL scheme eventually.
- `send_brief_ready` queries `users.fcm_token` — main-schema users, correct (Curia ids
  ARE harness ids — the identity decision from the port paying off).
- ipapi.co free tier (1k lookups/day, no key) is fine at prefs-save frequency; it does
  send user IPs to a third party — acceptable, but note it in any privacy copy.
